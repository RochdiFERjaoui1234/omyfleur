# O'my Fleur deployment

The artisan uses `/atelier`: log in, choose a photo, edit a product, save. Saving
writes to PostgreSQL. It does not commit to GitHub, trigger a build, or require
the artisan to use a hosting dashboard.

## Hosting and permanent storage

GitHub stores the source; Vercel builds and runs the app. **Those two services
alone do not provide permanent catalogue storage.** Keep the current PostgreSQL
connection and set its `DATABASE_URL` on the deployment. A pooled Neon connection
works with this app. Vercel Marketplace database integrations are still separate
storage services with their own limits.

Permanent storage does not require a paid plan: Neon currently offers a **$0 plan
with no credit card required** and 1 GB of database storage per project. Its free
compute and storage quotas still apply; see <https://neon.com/pricing>. Keep the
project on Free to avoid a paid subscription.

Vercel Hobby is restricted to personal, non-commercial projects. A florist
catalogue is commercial even when orders happen through WhatsApp. Optimisation
does not change that restriction: use an eligible hosting plan/provider for the
live business. See <https://vercel.com/docs/limits/fair-use-guidelines#commercial-usage>.

## One-time operator configuration

Set these **server-side** deployment environment variables (never `VITE_`):

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Permanent PostgreSQL connection string; use the pooled endpoint with TLS. |
| `ATELIER_PASSWORD_HASH` | Scrypt hash generated by the credential utility. |
| `ATELIER_SESSION_SECRET` | Independent random secret generated by that utility. |

The operator utility `npm run atelier:credentials` creates a new random owner
password, its hash, and a session secret, without writing files. Give only the
password and the `/atelier` bookmark to the artisan. Put the other two values in
the hosting environment settings. The previous source-embedded credentials are
retired; do not reuse them. Do not commit the generated output or build folders.
This is initial provisioning; there is no password recovery/change feature.

The Vercel build checks required configuration before building, then applies
pending migrations. Include all `migrations/*.sql` files. The new migration moves
previously uploaded Base64 photos into a separate binary-photo table and preserves
the products. Malformed legacy data causes a rollback instead of being discarded.
Use separate databases for preview deployments and production if both are enabled.

## Resource use

- Existing `/catalog/` images remain static CDN assets.
- New uploads are resized in the browser (up to 1280 px, at most 350 KB) and sent
  as binary, not Base64. Only a changed photo is uploaded on save.
- PostgreSQL still holds uploaded photos for now, as requested. Catalogue queries
  return short `/media/<content-hash>` references rather than image bytes.
- Photo responses are immutable and cacheable by browsers and the CDN. Identical
  uploads share a photo; replacing/deleting the final product reference removes
  its stored bytes in the same transaction. Already cached public images may
  remain in caches until they expire.
- The public catalogue has a 30-second shared-cache lifetime. The owner panel and
  authentication responses are never cached. No polling, cron, rebuild-per-edit,
  or external image-optimisation service is required.
- Login throttling lives in PostgreSQL, shared across server instances. The pool
  is bounded to two connections per instance with short idle/query timeouts.

Database storage and photo cache misses still count against the providers' usage
limits. This is a modest-catalogue approach, not unlimited free image hosting. A
later object-storage migration can keep exactly the same owner workflow.

## Local preview

Without `DATABASE_URL`, development uses the explicitly labelled, temporary
PGlite database. `npm run preview` enables that fallback only for local build QA;
Vercel ignores this escape hatch and requires permanent storage. The local panel
also requires real configured owner credentials. No default password is shipped.

An operator can provision local server credentials outside the repository, in
the per-workspace file returned by `localStoreConfigPath()` in
`scripts/local-store-env.mjs`. The development/preview launcher and migrator read
only `DATABASE_URL`, `ATELIER_PASSWORD_HASH`, and `ATELIER_SESSION_SECRET` there.
Explicit environment variables take precedence. Vercel ignores this local file
and always uses the deployment's server-side environment settings. No plaintext
owner password or database credentials belong in the source tree.

`startup.sh` remains the sandbox restart entrypoint. It delegates to the same
idempotent `scripts/start-dev.mjs` launcher used on Windows, which starts
`npm run dev` and leaves it running. `npm run typecheck`, `npm run test:store`, and
`npm run build` are the store's verification commands.
